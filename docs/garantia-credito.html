Garantia de crédito

Um Documento Fiscal (DF) de entrada gera crédito tributário de IBS/CBS para o comprador; um DF de saída gera débito para quem vende. Pela Lei Complementar 214/2025, a apuração do IBS/CBS é não cumulativa e opera por compensação "tributo contra tributo": o débito de uma saída é settled abatendo-se os créditos já appropriateds. O Splithub acompanha esse ciclo de vida por valor de cada DF e avisa seu sistema a cada mudança de status através de dois webhooks.

Diferente do ICMS, em que bastava o destaque do imposto na nota, o direito ao crédito de IBS/CBS depende do pagamento efetivo do tributo na própria NF de entrada. Na apuração da IBS/CBS, débitos e créditos são compensados de forma agregada por período; o Splithub modela esse ciclo por valor de cada DF para dar rastreabilidade a cada crédito e débito individualmente.

Ciclo de vida do crédito e do débito

Fluxo completo, por valor de cada DF:

1. O fornecedor emite uma NF de entrada para o comprador → nasce um crédito not_appropriated.
2. O tributo dessa NF de entrada é pago → o crédito passa a appropriated.
3. O adquirente (o mesmo comprador, agora na ponta de venda) emite uma NF de saída → nasce um débito not_settled.
4. Essa NF de saída é abatida pelos créditos appropriateds disponíveis (compensação tributo contra tributo) → o crédito utilized nessa compensação passa a utilized e o débito correspondente passa a settled, simultaneamente.

TributoStatusQuando ocorre
Créditonot_appropriatedNF de entrada emitida pelo fornecedor; o tributo dessa NF ainda não foi pago
CréditoappropriatedO tributo da NF de entrada foi pago
CréditoutilizedO crédito appropriated foi usado para abater (compensar) o débito de uma NF de saída
Débitonot_settledNF de saída emitida pelo adquirente; ainda não foi abatida por créditos
DébitosettledA NF de saída foi abatida pelos créditos appropriateds disponíveis (compensação tributo contra tributo)

Webhook event: mudança de status do crédito

Disparado sempre que o crédito tributário referente a um DF de entrada muda de status (not_appropriated → appropriated → utilized). No exemplo abaixo, o crédito acabou de ser utilized para compensar o débito de uma NF de saída — por isso o evento traz também a compensated_debt_dfe_key.

POST {sua_url_de_webhook} 
{
  "event": "credito.status_alterado",
  "created_at": "2026-07-29T15:00:00.000Z",
  "data": {
    "dfe_key": "35260714200166000187550010000012341234567890",
    "tax_type": "cbs",
    "credit_amount": 9.00,
    "previous_status": "appropriated",
    "current_status": "utilized",
    "change_reason": "outbound_debt_offset",
    "compensated_debt_dfe_key": "35260714200166000187550010000098769876543210"
  }
}

Seu endpoint deve responder 200 OK para confirmar o recebimento. Sem essa confirmação, o Splithub reenvia o evento.

CampoTipoDescrição
eventstringNome do evento: credito.status_alterado
created_attimestampData e hora em que o evento foi disparado
data.dfe_keystringChave de acesso do DF de entrada que originou o crédito
data.tax_typestringTributo do crédito: ibs ou cbs
data.credit_amountnumberValor do crédito referente a este DF
data.previous_status / current_statusstringnot_appropriated, appropriated ou utilized
data.change_reasonstringinbound_tax_payment (not_appropriated → appropriated) ou outbound_debt_offset (appropriated → utilized)
data.compensated_debt_dfe_keystringPresente quando current_status é utilized: chave da NF de saída cujo débito foi compensado por este crédito

Webhook event: mudança de status do débito

Disparado sempre que o débito tributário referente a um DF de saída muda de status (not_settled → settled). A extinção ocorre quando a NF de saída é abatida pelos créditos appropriateds disponíveis — por isso o evento traz também utilized_credits, com a chave e o valor de cada crédito usado na compensação.

POST {sua_url_de_webhook} 
{
  "event": "debito.status_alterado",
  "created_at": "2026-07-29T15:00:00.000Z",
  "data": {
    "dfe_key": "35260714200166000187550010000098769876543210",
    "tax_type": "ibs",
    "debt_amount": 1.00,
    "previous_status": "not_settled",
    "current_status": "settled",
    "extinction_type": "inbound_credit_offset",
    "utilized_credits": [
      { "dfe_key": "35260714200166000187550010000012341234567890", "utilized_amount": 1.00 }
    ]
  }
}

Seu endpoint deve responder 200 OK para confirmar o recebimento. Sem essa confirmação, o Splithub reenvia o evento.

CampoTipoDescrição
eventstringNome do evento: debito.status_alterado
created_attimestampData e hora em que o evento foi disparado
data.dfe_keystringChave de acesso do DF de saída que originou o débito
data.tax_typestringTributo do débito: ibs ou cbs
data.debt_amountnumberValor do débito referente a este DF
data.previous_status / current_statusstringnot_settled ou settled
data.extinction_typestringinbound_credit_offset
data.utilized_creditsarrayCréditos (dfe_key + utilized_amount) usados para compensar este débito
